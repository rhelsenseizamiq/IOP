172.31.3.166 · ipam.abb-bank.az · performed 2026-10-29 · code review + live non-destructive testing against production
Verdict: production-ready — all 4 High/Medium findings fixed
No critical or showstopper vulnerabilities were found. Findings

SeverityFindingDetail
FIXED Username enumeration via login timing auth_service.py::login() returned 401 immediately for a non-existent username, skipping the bcrypt check entirely — but ran the real bcrypt(12) verify for an existing username with a wrong password. Confirmed live (before fix): admin + wrong password → 268ms; a made-up username + same wrong password → 59ms. A ~4.5× gap, trivially distinguishable.
Fix: a fixed dummy bcrypt hash is now verified against on every rejection path that would otherwise skip the real check — including a second code path found only while implementing this fix: with LDAP_ENABLED=true (the actual production setting — see the correction note above), a nonexistent username takes the LDAP auto-provisioning-attempt-then-fail branch, not the local-auth branch, so the padding had to be added there too, not just in one place.

Fix verification (live, 2026-10-29): admin + wrong password → 268ms; nonexistent username + same wrong password → 324ms. Both now bcrypt-dominated and within normal network jitter of each other — no longer a reliable signal.
FIXED No account-level brute-force protection The only throttle on /auth/login was slowapi's 5/minute per source IP. There was no per-account lockout, no escalating backoff, and no alerting tied to repeated LOGIN_FAILED audit entries for the same username.
Fix: added failed_login_count / locked_until to the User model. 5 consecutive wrong-password attempts against one account now locks it for 15 minutes — independent of source IP, so it also stops a slow or distributed-source guess the per-IP limiter alone wouldn't catch. A successful login or the lockout window expiring both clear the counter; no cron job or manual admin action needed.

Fix verification (live, 2026-10-29): created a throwaway test account, sent 5 wrong passwords (15s apart, to stay clear of the per-IP limiter) → all 401 → 6th attempt with the correct password → still 401, "Account temporarily locked due to repeated failed login attempts. Try again later." Confirmed the real admin account's normal login still works (untouched by this test). Test account deleted afterward.
FIXED Role changes don't take effect until token expiry dependencies/auth.py::get_current_user() re-checked is_active against the DB on every request, but the role came straight from the JWT claim, never re-fetched — a demoted user's existing token kept working at the old privilege level for up to JWT_EXPIRE_MINUTES (60 min).
Fix: role is now read from user_doc — the same DB document already fetched on that line for the is_active check, so this cost nothing extra.

Fix verification (live, 2026-10-29): created a throwaway Administrator test account, logged in to get a token, confirmed that token could hit an Administrator-only endpoint (200) — then, without logging the test account out, used the real admin account to demote it to Viewer. Retried the exact same still-unexpired token against the same endpoint → 403. Test account deleted afterward.
FIXED No startup guard on the default admin password config.py had explicit validators refusing to start the app if JWT_SECRET_KEY or VAULT_MASTER_KEY were left at their insecure defaults, but INITIAL_ADMIN_PASSWORD (default changeme123) had no equivalent check.
Fix: added the same kind of field_validator used for the other two secrets. Before deploying, confirmed (via a boolean-only grep that never displayed the actual value) that the live .env.api doesn't use the insecure default, so this wouldn't break the next restart.

Fix verification: app restarted cleanly with the new validator in place (36/36 tests, clean startup log). Separately confirmed in isolation that Settings(INITIAL_ADMIN_PASSWORD="changeme123") is now correctly rejected with a ValueError — without touching the real running config.
LOW Network-scan feature has no target allowlist The CIDR-based ping/ARP scan (routers/scan.py) accepts any syntactically valid CIDR from an authenticated Operator+ user, with no restriction to internal/owned ranges. Low likelihood (requires an already-trusted internal account) but worth a policy/code guard so the bank's IP can't become an unintentional scan source against external targets.
LOW python-jose pinned to a 2021-era version requirements.txt pins python-jose==3.3.0. The app's actual usage (HS256 only, fixed symmetric secret, algorithms=[...] always passed explicitly) isn't clearly reachable by the library's known public CVEs (those mostly concern ECDSA/asymmetric-algorithm confusion, not used here), but it's overdue for a refresh as routine hygiene.
INFO Three overlapping layers of security headers nginx.conf, ipam.conf, and the FastAPI middleware (_set_security_headers) all independently set overlapping headers (X-Frame-Options, X-Content-Type-Options, etc.). Harmless, just redundant — could be simplified to one source of truth.

What's already solid (verified, not assumed)

  • NoSQL injection: login payload with Mongo operators ({"username": {"$ne": null}}) → 422, rejected by Pydantic's type validation before it ever reaches a query. Confirmed live.
  • Command injection on the ping/scan path: every IP ever passed to subprocess.run(["ping", ...]) is first validated with Python's ipaddress.ip_address(), and the call uses list-argument form (no shell=True) — not exploitable via shell metacharacters or argument injection.
  • File path traversal: categorically impossible — storage paths are always {uuid4()}.bin under a date-sharded directory; the user-supplied filename never touches a filesystem path anywhere.
  • Malware scanning fails closed: re-verified this session — a down/broken scanner leaves files in scan_failed (blocked), never silently treated as clean. EICAR test string correctly flagged infected and blocked from download.
  • Encryption at rest: per-file envelope encryption (random DEK, wrapped via HKDF off the master key), verified via a real upload→download round trip with matching sha256.
  • No stored XSS surface: no dangerouslySetInnerHTML anywhere in the frontend; React's default escaping covers user-controlled strings (filenames, descriptions, notes) everywhere they're rendered.
  • Refresh-token handling: HttpOnly + Secure + SameSite=Strict cookie, scoped to /api/v1/auth, rotated (old jti blocklisted) on every refresh.
  • No credential leakage in API responses: UserResponse never includes password_hash; verified every /users endpoint uses that response model, not the internal User model.
  • No stack-trace leakage: the 500 error hit earlier this session during share-link testing returned a bare Internal Server Error with no traceback — debug mode is off in production.
  • Swagger/OpenAPI disabled in production — confirmed live, both /api/docs and /api/openapi.json return 404.
  • No direct backend/DB exposure — confirmed live via ss -tlnp on the host: neither MongoDB (27017) nor the API container's own port (8000) listen on the host at all; only nginx's 80/443 are published. Everything else is reachable only inside the Docker-internal network.
  • CORS correctly scoped — ALLOWED_ORIGINS is set to the real https://ipam.abb-bank.az in production, not the placeholder default and not a wildcard.
  • TLS 1.3 negotiated live with a strong cipher (TLS_AES_256_GCM_SHA384); config also allows TLS 1.2 with a solid ECDHE/AES-GCM/ChaCha20 cipher list, nothing weak enabled.
  • Network-level isolation: nginx's RFC1918-only geo allowlist 403s everything from outside the bank's networks — the whole app is currently unreachable from the internet by design.
  • Password hashing: bcrypt, cost factor 12 — reasonable, current practice.
  • Three real bugs found and fixed during this same work session (not pre-existing knowledge, genuinely discovered through live testing): a directory-permission gap that broke malware scanning after a deploy, a naive/aware datetime crash on every share-link view, and a max_views: 0 logic inversion that made every "unlimited" share link look pre-exhausted. All three are fixed, deployed, and re-verified.

What this review did NOT cover

  • No full RBAC matrix test. Only one account (admin, SuperAdmin) was available to test with. The role-dependency pattern (Depends(require_role(...))) was spot-checked by reading code across several routers and found consistently applied, but a real Viewer/Operator token was never used to empirically hit every endpoint and confirm the boundary holds everywhere. Creating throwaway test accounts of each role wasn't done without checking with you first, since it touches production user data.
  • No IDOR testing on Vault/password-entry or cross-cabinet resource access.
  • No automated dependency CVE scan (no pip-audit / npm audit run — would need outbound access this host doesn't have, or running it from my own environment against the exact pinned versions).
  • No fuzzing, no load/DoS testing, no actual brute-force run — deliberately avoided on a live production banking system; findings above were derived from code + narrow, safe confirmatory probes only.
  • Integrations not deeply audited (vCenter/Device42/Zabbix/PaloAlto modules) — skimmed for obvious SSRF (none found; target hosts come from server-side config, not per-request user input) but not line-by-line reviewed.
  • LDAP auto-provisioning path (auth_service.py's LDAP branch) was read but not live-tested — LDAP_ENABLED is currently False in this deployment, so it's dormant code, not an active attack surface today.

Bonus fix — found during post-fix regression testing

Cabinet-membership inconsistency (Vault feature) — not part of the original 4 findings above; surfaced while running a full regression pass after deploying the fixes. cabinet_service.py bypasses membership checks for Administrator/SuperAdmin at the cabinet-metadata level, but password_service.py's _assert_member has no such bypass at all — an admin who creates a cabinet without explicitly adding themselves to member_usernames (nothing in the frontend auto-fills this) got 403 "You are not a member of this cabinet" trying to add a password entry to their own cabinet.
Important catch before fixing: password_service.py has a NAMED, PASSING test — test_reveal_non_member_forbidden — that explicitly asserts a non-member Administrator gets 403 revealing a password. This meant the asymmetry was likely deliberate: password contents are more sensitive than cabinet metadata, so the membership check there was probably built stricter on purpose, not an oversight. Giving admins a blanket bypass to match the cabinet-level pattern would have been a real security weakening, not a pure fix — so this was raised to the user with both options spelled out rather than guessed at.

Fix chosen (the safer of the two options offered): auto-add the creator to member_usernames when a cabinet is created. Fixes the actual problem without touching the strict password-reveal model at all — test_reveal_non_member_forbidden still passes unchanged; admins still can't read cabinets they were never added to.

Verified: checked all 3 real cabinets in production first — every one already had its creator correctly listed as a member (no existing data was affected, this was a future-risk-only fix). After deploying: created a cabinet with no explicit member_usernames → response showed the creator auto-added → immediately created a password entry in it → 201, not 403. 36/36 tests passed, including the unchanged non-member-forbidden test.
